Your agents already run commands. This writes them down.

numbat is a single Go binary that sits on the endpoint and turns what your coding agents actually do — files read, commands proposed, URLs fetched — into one typed, greppable record stream. It reads what agents already wrote to disk, and it can hook into them live. Detection runs on the machine. Nothing leaves unless you point it somewhere.

In plain terms

Three things it does, described the way you'd describe them to Kallen.

Strip the security vocabulary and it's an accountant, a smoke alarm, and a black-box recorder — running on the same laptop as the agent, not in someone's cloud.

Accountant

It writes down what the agent did

Every command, file touch, URL, and MCP call becomes one line of JSON with a timestamp, session ID, project path, and which agent did it. You get a searchable ledger of agent behavior instead of a chat transcript you'd have to read.

Smoke alarm

It flags the shapes that matter

About fifty built-in rules watch for known-bad patterns: reading a credential file, piping a download into a shell, writing to authorized_keys, hitting cloud metadata. Six of them are multi-step — read a secret, then upload something.

Black box

It reconstructs sessions after the fact

Agents already leave transcripts on disk. numbat parses those directly, so you can investigate a machine you never instrumented — including one you're handed after something went wrong.

How the data moves

Three ways in. One event model. One rule engine.

This is the whole architecture. Whether a record arrives from a live hook, an OpenTelemetry log, or a JSONL file on disk, it gets normalized into the same shape and evaluated by the same CEL rules. That's why a rule you write for forensic scanning also works live.

The part worth internalizing: hooks are the only path that can stop an action, because they're the only path the agent waits on. OTLP and at-rest scanning are observation only — by the time the record exists, the thing already happened.

Monitor vs enforce

Everything ships monitor-only. Blocking takes three deliberate steps.

Out of the box numbat never denies anything — every shipped rule is detection-only, and --enforce is off. Turning on blocking is not a flag flip: you have to copy a rule out, mark it, and reinstall.

Getting it running

Climb it in three rungs. Don't skip to the third.

Each rung is reversible and each one changes more state than the last. Rung one touches nothing at all — that's where a first afternoon with it should end.

RUNG 1
Read-only · changes nothing

Install the binary and look backwards

Verify the checksum, drop the binary on PATH, then point it at what's already on disk. agents tells you which agents it found and whether numbat is wired into them. scan replays their existing transcripts through the rules. Neither installs a hook or edits agent config.

# after downloading the darwin-arm64 asset + checksums
shasum -a 256 -c numbat_checksums.txt --ignore-missing
xattr -d com.apple.quarantine ./numbat 2>/dev/null
sudo mv numbat /usr/local/bin/ && numbat version

numbat agents # what's on this box, and is numbat wired in?
numbat scan # findings from existing transcripts → stdout
numbat timeline --agent claude # chronological session replay
RUNG 2
Edits agent config · still never blocks

Wire up live capture, monitor-only

This writes a numbat hook command into the agent's own settings file — for Claude Code that's ~/.claude/settings.json. Read the diff before and after. hook status confirms the config is present; it does not prove the hook actually fires, so generate real activity and watch the file grow.

git diff --no-index /dev/null ~/.claude/settings.json > /tmp/before.txt

numbat hook install --agent claude --emit all
numbat hook status --agent claude

# now do something in Claude Code, then:
tail -f ~/.numbat/records.ndjson | jq -c '{t:.timestamp, k:.record_type, a:.source_agent, r:.rule_id}'
RUNG 3
Can interrupt live agent work

Promote one rule to enforce

You cannot enforce a shipped rule in place. Copy its YAML into a directory you control, keep the same id, add enforce: true, bump the version, validate, then reinstall pointing at that directory. Install refuses to proceed if the compiled catalog has no enabled enforcing rule — so a typo fails loudly instead of silently doing nothing.

mkdir -p ~/numbat-policy
# copy rules/persistence/ssh_authorized_keys.yaml from the repo,
# keep the id, add `enforce: true`, bump `version`

numbat rules check --rules-dir ~/numbat-policy
numbat rules list --rules-dir ~/numbat-policy

numbat hook install --agent claude --emit all \
  --rules-dir ~/numbat-policy --enforce

Fish shell note: the docs use VAR=x command inline assignment, which bash accepts and fish does not. Use env NUMBAT_HTTP_TOKEN=… numbat ship … or set it with set -x first. Auth secrets are read from the environment only — they're never accepted as flags and never written into hook config.

Where the logs live

One NDJSON stream. Five record types. Click a field.

Default paths sit under ~/.numbat/: findings.ndjson if you only asked for findings, records.ndjson once you add events or indicators. numbat never rotates these files — retention is yours. Below is a finding of the shape you'd get if an agent read a secrets file and then proposed an upload.

The trap in that record: confidence is not "how likely is this malicious." It's how sure the parser is that it read the source correctly. A high-severity, high-confidence finding still only means a rule matched a proposed action — pre-action hooks fire before the thing happens, so a finding never proves the command ran.

What it looks for

The shipped catalog, grouped by what an attacker would be doing.

These are the built-in rule IDs. All monitor-only. The last group is the interesting one — sequences correlate two steps inside a window, which is where single-event detection usually falls down.

Expect noise on your boxes specifically. An autonomous fleet running with reduced approval modes will trip tamper.guardrails_off and exec.agent_runtime_bypass_flags constantly. Governance work that edits hooks and settings trips tamper.agent_config_write. Baseline with a full scan first, see what fires against normal operation, then decide which rules to disable by ID before you ever consider enforce mode.

Beyond one laptop

Rolling it onto builder machines without building a SIEM.

numbat is a single static binary with no daemon and no cgo, so distribution is just copying a file. The two decisions that matter are how records get off the box, and whether you can tell the boxes apart.

Identity

Tag each endpoint

Every record already carries hostname, OS, arch, and username. Set NUMBAT_DEVICE_ID in each machine's environment to add a stable opaque ID, so a rebuilt or renamed machine still joins to its own history.

Delivery

Write to file, ship separately

Direct HTTP from the hook is not a durable queue — a failed batch retries once and then drops oldest-first. Write hooks to file, and run numbat ship alongside to tail that file to an ingest endpoint with at-least-once delivery and checkpointing.

Scope

Managed install for shared boxes

Claude Code, Codex, Cursor, Copilot, Gemini, Windsurf, Qwen, and Auggie expose admin-managed hook config. hook install --managed targets those instead of a single user's file — the right choice for a machine multiple people or agents use.

# on each builder box: capture to file, forward out of band
numbat hook install --agent claude --emit all \
  --output file --output-file ~/.numbat/records.ndjson

env NUMBAT_HTTP_TOKEN=$TOKEN numbat ship \
  --input-file ~/.numbat/records.ndjson \
  --http-url https://your-ingest/numbat \
  --http-auth bearer

Rotation is on you. numbat never truncates or rotates its own output, and ship never touches the input file. Without logrotate or equivalent, --emit all on an active agent fleet will grow unbounded. Start with findings-only on secondary machines and promote to full events where you actually need them.

Read this before you trust it

What it does not do.

The project is unusually honest about its own edges, which is a good sign. These are the ones that would actually bite you.

It's two days old

First public release landed 29 July 2026 at v0.1.1. Record schema is 0.2.0 and will move. Treat anything you build on the record shape as pinned to a version, and expect the rule catalog to churn.

A finding is not an incident

Rules match patterns. Pre-action hooks describe requests, not outcomes. Nothing here proves an action completed, and a scan can only ever see what the agent chose to persist.

Hooks aren't a security boundary

Enforcement only covers synchronous pre-action callbacks. Hosted tools that never touch the local hook path bypass it entirely, and most agents fail open on hook error or timeout. It raises the cost of a bad action; it doesn't prevent one.

Records hold sensitive context

Redaction runs before emission, but endpoint identity, project paths, and command text still land in the output. That file is now a thing worth protecting — and it's plaintext on disk by default.

The collector has no auth

The OTLP receiver ships with no TLS and no client authentication. Keep it bound to loopback. Anything that can reach it can inject telemetry into your own detection stream.

Installing it modifies your agents

Rung two writes a command into the config your agents execute — structurally the same class of change as a malicious hook install. The difference is that you initiated it and can read the diff. Read the diff.
